# Правила разработки Weatherpins

## Контекст проекта

- Weatherpins — личный учебный веб-проект на Django: интерактивная карта
  с фотографиями и погодными данными.
- Актуальный репозиторий — `sganzha81/weatherpins`. Используй имя `weatherpins`;
  упоминания прежнего названия считай устаревшими.
- Разработка ведётся преимущественно на Linux; production размещён
  на PythonAnywhere. Домен — `weatherpins.ru`, DNS — Beget,
  транзакционная почта — Resend.
- Фактическую архитектуру, версии зависимостей и конфигурацию определяй
  по текущему репозиторию. Перед изменениями изучай относящиеся к задаче
  код, документацию и локальные инструкции; при наличии README начинай с него.

## Обязательные ограничения

Без явного поручения пользователя не выполняй деплой, операции с production
и разрушительные операции с данными.

## Django development server

**Запуск development server разрешён только после явного согласия пользователя.**

### Проверка состояния при начале сессии

- В начале новой интерактивной сессии, до выполнения первого пользовательского задания, проверяй состояние локального Django development server Weatherpins.
    
- Выполняй проверку безопасно, не запуская сервер и не изменяя состояние системы.
    
- Учитывай ограничения sandbox: отсутствие процесса внутри изолированной среды не доказывает, что сервер остановлен.
    
- Если sandbox не позволяет достоверно определить состояние сервера, самостоятельно запроси разрешение на безопасную диагностическую команду вне sandbox.
    
- Если получить достоверный результат невозможно, сообщи об ограничении и предложи ручную проверку.
    

**Если сервер уже работает:** продолжай выполнение пользовательского задания без дополнительных вопросов.

**Если сервер не запущен:**

- Сообщи об этом пользователю.
    
- Покажи конкретную команду запуска с учётом текущего окружения.
    
- Прямо спроси, хочет ли пользователь запустить сервер.
    
- Остановись и дождись ответа, прежде чем приступать к основному заданию.
    
- Не заменяй вопрос информационным сообщением о возможности ручного запуска.
    
- Предлагай запуск независимо от того, требуется ли работающий сервер для текущего задания.
    

**После ответа пользователя:**

- Если пользователь согласился, действуй согласно разделу «Запуск сервера», затем продолжай исходное задание.
    
- Если пользователь отказался, ничего не запускай и продолжай работу по своей текущей задаче.
    
- Не повторяй эту процедуру перед каждым последующим заданием в рамках той же сессии без необходимости.

### Запуск сервера

После явного согласия пользователя:

- Повторно проверь состояние сервера и доступность предполагаемого порта, чтобы избежать повторного запуска.
- Определи текущую ОС, корневую директорию проекта, Python-окружение и доступный системный терминал.
- Запускай Django из корня проекта, используя соответствующее Python-окружение.
- Используй отдельное окно обычного системного терминала Linux или macOS с подходящей командной оболочкой. Не привязывайся к конкретному эмулятору терминала или способу работы с Codex.
- Сервер должен продолжать работать независимо от Codex CLI, расширения VS Code и их сессий.
- Не запускай сервер в терминале самого Codex или как скрытый фоновый процесс.
- Если технические ограничения не позволяют открыть отдельный системный терминал, объясни причину и предоставь точную команду для ручного запуска.
- Сообщай фактический результат запуска. Не утверждай, что сервер работает, без подтверждения.

Если пользователь отказался от запуска, ничего не запускай и не повторяй предложение без необходимости. Отсутствие сервера не должно блокировать выполнение основной задачи.

### Ограничения

- Не запускай второй экземпляр уже работающего сервера.
- Не останавливай работающий сервер без явного разрешения пользователя.
- Не изменяй автоматически порт, если он занят, и не завершай чужие процессы для его освобождения.
- Не запускай временные HTTP-серверы или дополнительные экземпляры Django без отдельного согласия.
- Не занимай порты `8000/8001` посторонними процессами.
- Для `python manage.py check`, автоматизированных тестов и статических проверок запуск development server не требуется.

## Принципы разработки

- Используй стандартные практики Python и Django, предпочитай простые,
  понятные и поддерживаемые решения.
- Избегай избыточных абстракций, ненужных зависимостей и преждевременной
  оптимизации.
- Вноси минимально достаточные изменения в рамках задачи, без необоснованного
  рефакторинга соседнего кода. Сохраняй совместимость с существующим функционалом.
- Не меняй архитектуру без практической необходимости. Для неоднозначных
  архитектурных решений до реализации объясняй альтернативы и компромиссы.

## Безопасность

- Уделяй особое внимание аутентификации, авторизации, обработке пользовательских
  данных и валидации.
- При изменениях views, forms, models, API и настроек учитывай безопасность
  Django-приложения, включая права доступа, CSRF, XSS и обработку загрузок.
- Не раскрывай секреты, токены, пароли и другие чувствительные данные.
  Не добавляй их в репозиторий, исходный код или диагностические логи.

## Проверки изменений

- Для изменений Python/Django-кода используй `python manage.py check`,
  когда это применимо, и запускай релевантные автоматизированные тесты
  без поднятия сервера.
- Для HTML/CSS/JavaScript используй доступные статические проверки
  и существующие тесты.
- Не считай ручную проверку в браузере выполненной, если её фактически не было.
  Если проверка не выполнена, честно указывай причину.
- Для изменений исключительно документации не требуй тестов или Django-проверок
  без обоснованной необходимости.

## Коммуникация и отчётность

- Общайся с пользователем на русском языке. Имена переменных, технические
  термины, команды и элементы кода оставляй в оригинале.
- Существенные технические решения кратко обосновывай. Учитывай учебную цель:
  делай реализацию и её объяснение понятными пользователю.
- По завершении каждой задачи сообщай:
  - какие файлы изменены и что реализовано;
  - какие проверки выполнены и каковы результаты;
  - что осталось проверить вручную;
  - какие ограничения, риски или нерешённые проблемы остались
    (либо что они не выявлены).
